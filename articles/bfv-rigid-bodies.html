刚体物理四种实现对照

Havok、RigidSim、RigidSim 凸包版、BFVGpuSim

同一批农舍碎块，换了求解器，单栋全碎时的落点能相差二十多厘米。把 20 栋放在一起，CPU 和 GPU 的步进耗时又换了顺序。下面顺着一次 1/60 秒的物理步找原因。输入是凸包、初始位姿和同一份部件释放规则。每步输出刚体的新位置、朝向、接触事件和休眠状态。

一、一步物理模拟在做什么

以一块墙体碎片落到地板上为例，一步要回答四个问题。

  1. 宽相（broadphase）： 用便宜的包围体，快速筛掉肯定碰不到的物体对，只留下“可能碰到”的候选对。
  2. 窄相（narrowphase）： 对每个候选对算精确几何：碰没碰、法线朝哪、穿进去多深、接触点在哪。
  3. 求解（solver）： 根据所有接触点算冲量，让物体不再互相穿透、有摩擦、能叠起来。
  4. 休眠（sleep）： 静止够久的物体不再计算，直到被碰醒。

宽相给窄相一张候选清单，窄相把接触点和法线交给求解器。求解器改速度，积分更新位姿。休眠利用多帧的运动记录减少后续计算。同一份几何输入，到这几处都可能走不同的路。

三、宽相

Havok：SAP（Sweep and Prune）

把每个物体的包围盒投影到 x、y、z 三根轴上，得到三组区间，各自按端点排序。两个物体只有在三根轴上的区间都重叠时，才可能碰到。

SAP 的关键是增量更新。物体每帧只移动一点，排好序的端点通常只需做少量交换。重叠关系变化后，宽相增删候选对。已经接触的物体仍可能需要更新接触点。

RigidSim 和 BFVGpuSim：空间哈希

把空间切成边长相同的格子，每个物体按中心落进一个格子（用哈希表存）。找邻居时只看自己这一格和周围 13 个“正向”邻格（26 个邻格里只取一半，避免同一对算两次）。

空间哈希容易并行。这个 GPU 实现每步清空哈希表，把物体重新插入，再配对。场景已经静止时，这部分工作仍可能产生固定开销。

BFVGpuSim 多了一个大物体列表：农舍的整面墙直径可达 15 m，远大于格子，13 个邻格覆盖不到。这类物体单独放一张表，每个物体都和它们测一遍。

四、窄相

RigidSim：解析公式

球对球只要比较球心距离和半径之和。球对盒、盒对盒各有专门的检测。农舍墙块有斜面、断口，换一个外接盒来算，会把盒子角上原本空着的地方也算成实体。

凸包碰撞的三件工具

换成任意凸多面体后，这里把距离、穿透方向和接触点分开算。

GJK（求距离）： 两个凸包 A、B 是否相交，等价于“闵可夫斯基差 A−B 是否包含原点”。GJK 不需要把 A−B 真算出来，只要能回答一个问题：“沿方向 d，形状最远的点在哪？”（支撑函数，遍历顶点取点积最大的那个）。用这些最远点组成一个单纯形（点、线段、三角形、四面体），每一轮朝原点推进一步，直到包住原点（相交），或者确认推不过去（分开，并得到最近距离和方向）。

SAT（分离轴定理）。 找一条轴，使两个凸多面体的投影分开。候选轴来自两边的面法线和非平行边对的叉积。若投影全有重叠，就沿各单位轴比较把投影移开的距离，取最小值。发生区间包含时，要算移出所需的距离，不能直接取交集长度。本项目用 SAT 补上 GJK 相交测试没给出的穿透方向和深度。

面裁剪（求接触点）： 有了法线以后，在一边选最正对法线的面（参考面），另一边选最背对的面（入射面），把入射面的多边形按参考面的边裁剪，留下在参考面下方的点，最多取 4 个。只用一个接触点的话，平面贴平面的碎块会绕着这个点摇晃，所以要多点。

Havok 的 GSK 和凸包外壳

工程里的 Havok 农舍凸包带约 1 cm 的壳（convex radius）。GJK 量两个内核之间的距离，再减去两层壳的半径。两块碎片贴合时，内核还可能留着空隙，这时已有距离和法线。核心也重叠时，需要额外计算穿透。这里能解释壳怎样减少深接触，不能据此把 GPU 的 SAT 路径套在 Havok 上。

GSK 还有两样缓存：

  • 单纯形缓存： 记住上一帧 GJK 最后用到的那几个顶点，下一帧从它们开始，物体几乎没动时 1 轮就收敛。
  • TIM 提前跳过。 记住上一步的分离方向和距离，再用本步平移和转动能带来的最大接近量作保守估计。如果这对物体仍隔得足够远，就跳过本步的精确距离查询。

再加上持久流形：接触点跨帧保留，每帧只增减变化的点。

SAT 轴缓存：浅接触沿用上一帧找到的那条轴，只重新量一下深度；每 8 帧做一次全量，防止轴过时。

原笔记记过同一堆 3000 块的计数。关闭缓存时，GJK 一帧迭代约 11 万次，打开后约 1 万次，约六成的候选对被 TIM 跳过。这组数来自随机凸包堆，不能拿来作单栋农舍的计数。

变体 0 用原始外轮廓。碎块贴合时轻微重叠，就容易走到 SAT。原稿记录的一组 CPU 镜像采样里，约 73% 的 GJK 查询后面还要做 SAT。单次查询的耗时比受凸包复杂度影响，GPU 上要另看各阶段的计时。

五、求解：Jacobi 和 Gauss–Seidel

这一节是四套实现在“稳不稳”上最核心的区别。

一个接触要做什么

每个接触点要满足：沿法线的相对速度不小于目标值（不能继续往里钻），冲量只能推不能拉，摩擦力不超过 μ × 法向力。求解器给每个接触算一个冲量，加到两个物体上。

难点在于接触之间互相影响：一块碎片下面压着两块，上面压着三块，改一个接触的冲量，其他接触看到的速度就变了。

Gauss–Seidel（Havok 的做法）

一个接一个地算：算完第一个接触，立刻把冲量加到物体上；算第二个时，看到的已经是更新后的速度。全部过一遍叫一次迭代，Havok 每步做 4 次。

上一块向下传来的变化，后算的接触在同一轮就能用上。传播多远取决于接触处理顺序。在 CPU 上可以直接依次更新。

暖启动：每个接触记住上一帧的累计冲量，这一帧从它开始。静止堆叠时，每帧需要的冲量几乎一样，从上一帧的值开始，迭代一次就接近正确。没有暖启动，每帧都要从零重新“托起”整堆东西。

Jacobi（RigidSim 的做法）

所有接触同时算：每个接触都只看这一帧开始时的速度，各自算出冲量，最后全部加在一起。这很适合 GPU：每个接触一个线程，互不等待，用原子操作累加（RigidSim 把冲量换成 int32 定点数，用 InterlockedAdd 加）。

两个问题：

  • 信息传得慢。 同一次 Jacobi 迭代里，接触看不到相邻接触刚算的冲量。上面一层突然受力，要经过多轮才能影响最下面那层。这里的 RigidSim 每步只做一轮速度求解，也没有暖启动。
  • 会推过头： 一个物体同时碰到好几个邻居时，每个接触都按“只有我一个”去算冲量，加起来就太大了，下一帧再弹回来。RigidSim 给多点接触乘了 1/N 的权重来缓解，但堆叠时一个块往往有十几个接触。

把 RigidSim 的 Jacobi 接到农舍凸包上，变体 1/2 在单栋全碎时，最终高度的中位数均比 Havok 低约 27 cm。另一组 3000 块的随机凸包堆测试中，按记录的运动阈值，约 85% 的块还在动。Havok 开关休眠的两次对照都只剩约 20 块在动。是否在动和引擎是否已将刚体标成休眠，是两个不同的计数。

着色 Gauss–Seidel（BFVGpuSim、变体 3/4 的做法）

GPU 上想要 Gauss–Seidel 的效果，又要并行，办法是着色：把接触分成若干“颜色”，同一种颜色里的接触两两不共享物体，所以可以并行算，不会互相干扰；颜色之间按顺序来，后一种颜色能看到前一种的结果。这在颜色之间就是 Gauss–Seidel。

  • 怎么着色： 每一轮，每个还没着色的接触按一个随机优先级去“认领”它的两个物体，同时拿下两个物体的接触就得到这一轮的颜色；其余的留到下一轮。
  • 按凸包对着色： 同一对凸包的 4 个接触点放在同一种颜色里，由一个线程依次处理。如果按单个接触点着色，堆叠时一个物体身上有四五十个接触点，需要的颜色远多于上限，多出来的就只能单线程串行处理，会非常慢。
  • 同步代价。 每种颜色要等上一组写完。假定活跃颜色有 20–30 种，变体 0 的 4 次速度迭代加 2 次位置迭代就有 120–180 个颜色阶段。屏障的范围取决于实现，这个乘积不能用作整帧的 GPU 派发次数。

由变体 1 换到变体 3，RigidSim 参数保留，着色 GS、暖启动和窄相缓存一起换了进来。单栋全碎的中位高度差由 −27 cm 变为 +0.5 cm，变体 3 仍一直醒着。20 栋的中位差为 +3.6 cm。农舍这组实验说明整套改动有效，各项的独立贡献还要拆开测。

六、穿透修正

物体总会有一点穿透（离散时间步、数值误差、美术摆放时本来就重叠）。怎么把它推出来，三种做法：

穿透修正怎样影响下一帧
做法优点缺点
Baumgarte 偏置（Havok、变体 3/4）在速度求解里，给目标速度加一项“穿透深度 × 系数 ÷ dt”，用速度把物体推开简单，一次求解搞定推开的速度会变成真实动能，物体被“弹”出去
单独位置推出（RigidSim）速度求解之后，再做一次只改位置的 Jacobi不进速度同样受 Jacobi 传得慢的限制
分离冲量（BFVGpuSim）位置修正用另一套“伪速度”单独求解，只用来改位置，用完就丢推开不产生动能多一组迭代

这组农舍碎片起始摆放有重叠，原笔记记录的最大值是 28 cm。CPU 镜像测试时，强行通过速度把它们推开会给碎块增加动能，落地后仍在抖。变体 0 因此单独修正位置。

七、休眠

Havok：岛 + 位置参考盒

  • 岛： 通过接触连在一起的物体算一个岛。整个岛都满足条件才一起睡，有一个醒就一起醒。避免“下面的睡了，上面的还在压”这种状态。
  • 位置参考盒。 低速接触时，速度可能围着阈值反复跳。项目笔记用短期 2 cm、每 8 帧检查的较大 8 cm 参考范围解释这套思路。给物体留出小幅抖动的空间，观察它有没有持续向外漂。实际判定还要结合运动状态与岛的其他成员。
  • 求解器减速： 慢到一定程度的物体，每步额外减一点速度。

RigidSim：没有休眠

所有物体每步都参与计算。静止的碎块堆照样要跑宽相、窄相、求解。

BFVGpuSim 的岛和唤醒

岛在 GPU 上用标签传播算。每个接触把两端动态体的标签取最小值，再做几轮指针跳跃，找到连在一起的物体。这个后端配了位置参考盒、低速减速和碰撞唤醒，项目记录的一项接近速度阈值为 0.3 m/s。

单栋静止后，变体 0 的 GPU 步进约 0.4 ms，变体 1 仍在 3 ms 左右。两者还同时有窄相缓存和求解方式的差异。更直接的一组对照是变体 3 加岛休眠得到变体 4，静止耗时由约 1.5 ms 降到约 0.4 ms。

1. 活太少，GPU 吃不饱

原稿在单栋繁忙阶段记录了约 1000 对候选、300–500 个接触。若每对一个线程、每组 64 个线程，只需约 16 个线程组。线程组大小由着色器指定，硬件 wave 的宽度是另一件事。仅凭候选数，还算不出 GPU 的实际利用率。

批量小，能用来隐藏访存延迟的独立工作也就少。要确认瓶颈落在哪一项，需要结合硬件计数；本次留下的是阶段计时。

2. 每个线程的活又长又不一样

一对凸包的窄相在一个线程里串行做：GJK 每轮遍历所有顶点；穿透了还要 SAT（面 × 顶点，加上边 × 边 × 顶点，一对就是几千次投影）；最后面裁剪。不同的对，循环次数差别很大：

  • 同一个 wave 里的 32 或 64 个线程必须一起走，有一个线程还在跑 SAT，其他线程都得陪着等。
  • 碰到车身（156 个顶点、315 个边方向）的那几个线程会特别慢，整个 wave 被拖住。
  • 面裁剪用的局部数组较大，可能增加寄存器压力。是否发生了溢出，以及花了多少时间，要从编译结果或 GPU 计数器看。

原笔记在单栋阶段采样中记录了约 1.1–1.6 ms 的窄相、0.27 ms 的宽相和 0.2 ms 的求解。这个拆分能指出值得先看的阶段。把总时间除以候选对数量得到的是批次摊销值，不能当成单线程执行时长。

3. 固定开销：每一步约 0.4 ms

不管有没有东西在动，GPU 每一步都要付这些：

  • 多个计算阶段。 按版本不同，每步有二十余次 compute dispatch。存在数据依赖时，后面的 pass 要等前面写完。
  • 着色与求解。 算完一种颜色才轮到下一种。颜色数和迭代数都会增加顺序工作。
  • 每帧重建： 宽相要清空 8192 个哈希桶、所有物体重新插入、重新配对；SAP 只处理变化的部分。
  • 回读： 每帧把所有位姿和事件拷回 CPU。

所以全部静止时，BFVGpuSim 仍然要 0.4 ms，Havok 只要 0.006 ms。

4. Havok 可以跳过哪些工作

对照组的单栋物理步进均值为 0.34 ms。引擎能在几个层次利用上一帧的结果。

  • SAP 增量更新，物体没动时宽相几乎为零。
  • 有壳接触常可由核心距离给出法线，缓存单纯形给下一次距离查询提供起点，TIM 跳过有足够分离距离的候选对。
  • 睡着的岛整个不参与计算。
  • Gauss–Seidel 可以依次更新接触，省去 GPU 实现的着色步骤。这组测试没有报告 CPU 缓存命中率。

GPU 上分支和“跳过”都不便宜：一个 wave 里只要有一个线程不跳过，大家都得等它。

5. 凸包版变体 1 为什么停下来还贵

变体 1 没有窄相缓存，每帧重新找单纯形，也没有 TIM 和休眠。单栋碎落均值 3.44 ms，静止后约 3 ms。变体 2 加了休眠，但单栋还有 127 块没睡，维持在 2 ms 以上。两种配置都在做凸包碰撞。

6. 为什么 20 栋时反过来

20 栋提供了更大的批次，固定派发开销可以分摊。这个 UE 工程默认依次步进各栋的 Havok 世界，实测的 CPU 时间随栋数增加。两档规模足以说明这次排序发生反转，仍不足以画出一般场景下的性能交叉点。

GPU 路径在游戏线程上测得的提交耗时只有 0.007–0.018 ms，物理计算则和渲染共享 GPU。要判断玩家看到的帧率是否改变，还得看整帧的关键路径。

九、还能怎么变快

以下按 11 月 26 日整理时的进度区分。

  1. 让一个 wave 合作处理一对凸包。 顶点分给多个线程并行投影，再归约出支撑点。SAT 的面轴和边对也可切分。这仍是候选方案，收益要用同一批凸包复测。
  2. 给凸包加壳。 变体 5 已烘焙内缩几何，默认 1 cm，薄片试 5 mm、2.5 mm，仍然太薄的 45 个保留原轮廓。同时把窄相拆成两个 pass，并把休眠等待从 0.6 s 调到 1.5 s。20 栋步进均值 2.278 ms，P95 为 3.746 ms。这组改动是一起测的，不能把整段收益只算在碰撞壳头上。
  3. 尝试全睡后跳过整步。 工程试过不再派发，也减少了静止物体的姿态提交。原记录的静止计时反而从 0.36 ms 变为 3.2–4.2 ms，改动已回退。时间戳或异步读回错位是待查的解释。
  4. 合并 pass，减少同步。 可以尝试合并清空、积分、配对等相容的工作，在接触关系稳定时复用着色。还要验证刚体增删和新接触会正确使缓存失效。
  5. 改用排序宽相。 候选方案是按格子编号做基数排序，与当前重建哈希表的做法在同一规模下比较。资料中没有这项改动的实测结果。

十、四套实现各自适合看什么

  • Havok。 在本机 CPU 基线里，增量宽相、缓存和岛休眠尤其有利于单栋、小批量以及静止阶段。默认步进占用游戏线程。
  • RigidSim 原版。 空间哈希、解析形状、一次速度 Jacobi，适合观察最简 GPU 管线。要拿它解释农舍实测，先把形状换成凸包这一步算进去。
  • RigidSim 凸包版。 同样的几何和参数下，变体 3 的暖启动与着色求解能显著改善最终高度，加休眠后，变体 4 在单栋全碎场景通过了工程的对齐检查。个体轨迹和所有测试模式仍有差别。
  • BFVGpuSim。 变体 0 用窄相缓存、暖启动和岛休眠减少重复工作。在 20 栋测试中，这一路的 GPU 步进均值低于 Havok 的 CPU 步进均值。单栋和静止场景的结果提醒我们先看工作量，再选后端。

本页据 BFVDestructionUE5 项目的《学习－刚体物理四种实现对照》整理。方法与配置核对了 11 月 25 日《GPU 凸包刚体各版本对照》，11 月 26 日更新的 gpusim/VARIANTS.md 补齐了变体 5 的烘焙、A/B 测试与回退记录。表中数据为这些版本的已记录结果。

农舍测试机为 Ryzen 7 7700、RTX 5060 Ti。工程以 Havok 2013.2.0-r1 的测试构建作为基线。浏览器实验使用另一个 Havok 构建，零售版《战地 V》的逐帧求解轨迹也未进入这组对照。CPU 基线使用三角网格地面，GPU 路径使用平面。GPU 的重复运行可能发生漂移，例如变体 5 的单栋全碎在两次运行中分别得到 −0.5 cm 和 +16.2 cm 的中位高度差。
