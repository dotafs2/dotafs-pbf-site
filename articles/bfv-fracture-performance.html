分裂帧性能与原资产核对

2026-11-23 至 11-24 · 项目实验记录

一栋农舍有 3 个簇在同一帧碎开，分裂只花了 0.15 ms。把同一段破坏过程复制到 20 栋，整帧却要 39 ms。下面先看时间花在哪，再看哪些工作可以提前或推迟。计时来自我们的 UE 实验工程，CPU 对照用移植的 Havok 2013.2.0-r1。详细数字见分阶段性能报告，后两节记录 GPU 后端的实现和对照结果。

先把一次分裂拆开

起点是 ABFVFarmActor::Split。它原来只有一个总计时，all 场景里峰值 0.15 ms，看不出钱花在哪。这一帧里它做了几件事：读出整簇刚体的位姿，从 Havok 世界删掉它，给每个子块的句柄组件写位姿，再用预先准备好的形状 new hkpRigidBody，最后 addEntity。

addEntity 是黑盒，我在 hkpWorld.cpp 里加了三个 tick 时间戳，分成岛、宽相和回调三段。宽相这一段会顺手给新刚体和周围所有重叠的物体建碰撞代理。子块之间本来就贴在一起，所以这一步最贵。单栋峰值帧有 3 个簇同时分裂，激活 26 个刚体，新建 103 个碰撞代理。分裂合计 0.15 ms，其中宽相约 0.05 ms。

物理步进也拆了。hkpWorld::stepDeltaTime 在这个配置下（离散仿真、SAP 宽相、没有内存看门狗）就是依次调 integrate、collide、advanceTime。我逐行对过源码，确认两种调法等价，才把它拆成三段分别计时。这些计时都挂在 -bfvphaseprobe 上，默认构建不走这条路。

测到一半，单栋第一次分裂突然变成 4 ms。查下来是 hkStopwatch 第一次被调用时会 Sleep 校准时钟，正好落在第一次分裂的计时里。现在 bfvCreateWorld 里先调一次 getTicksPerSecond，这 4 ms 就没了。

单栋：没什么可优化的

单位 ms，数字是均值 / P95 / 最大：

单栋 all
生成并激活子块 0.10 / 0.15 / 0.15
物理步进（游戏线程） 0.34 / 0.67 / 0.91
画碎块，CPU 渲染线程增量 0.13 / 0.45 / 1.26
画碎块，GPU 增量 0.12 / 0.38 / 0.60

增量的测法是同一镜头、同一条破坏时间线跑两遍，一遍用 -bfvprobehide 把碎块组件设为不可见，物理照常模拟，两遍逐帧相减。单栋最大的单项是第一次脱落时注册渲染组件，每簇 0.3–0.5 ms。

20 栋：卡在游戏线程，但不卡在物理

20 栋同时碎时整帧 39 ms。其中游戏线程 35 ms，渲染线程 8 ms，GPU 5.7 ms，所以要看的是游戏线程。拆开以后：

  • EndOfFrameUpdates 15 ms：每帧把 440 个复合骨骼网格的骨骼数据交给渲染
  • 碎屑 ProceduralMesh 每帧重建 6.6 ms，偶发 171 ms
  • 物理步进 6.6 ms
  • 分裂 3.8 ms，峰值 8.3 ms。那一帧有 60 个簇分裂，激活 520 个刚体，新建 2060 个碰撞代理
  • 首次脱落最重的一帧 10.1 ms：60 个簇同帧注册渲染组件，其中渲染状态创建占 4.5 ms

能挪的挪走，不能挪的不动

先看哪一步值得提前做或异步做。碰撞代理是 addEntity 同步建的。改用 addEntityBatch 或推迟加入都会改变岛和接触的顺序，结果就和基线对不上了，所以这一步不动。渲染组件不参与物理，晚一两帧建不影响任何事件。

  • -bfvdefervisuals：脱落时只建刚体，渲染组件进队列，所有农舍共用每帧 1 ms 的预算慢慢建。组件建好的那一帧才隐藏完好的墙，中间不会露洞。如果这时要分裂，就当场先把组件建好。20 栋首次脱落那一帧从 10.1 降到 1.4 ms。
  • -bfvparallelstep：20 个世界本来就互不相干。我在 DLL 里放了一个工作线程池，每个线程有自己的 hkMemoryRouter。ABFVStepCoordinator 等所有农舍的前半步跑完，把 20 个世界一起交给线程池，再按原来的顺序跑各农舍的后半步。物理占游戏线程的时间从 6.6 / 15.4 降到 1.0 / 2.5 ms。代价是各线程耗时加起来 10.3 ms，总 CPU 多了约 55%。

两个开关都开时，游戏线程 35.0 → 29.2 ms，帧时间 39.3 → 34.3 ms。开着这两个开关，release、drive、shoot、all、stress 五项逐事件、逐碎块高度都和 11-21 的基线一致（Tools/TestVariants.ps1）。

碎屑也试过一次：把 CreateMeshSection 换成 UpdateMeshSection 加预留容量。游戏线程只省了 1 ms，渲染线程却从 9.4 涨到 34 ms。UE 5.8 的 UpdateMeshSection 每帧都在渲染线程把整段顶点缓冲重写一遍，20 栋乘上几个 section 就是这个数，所以这个改动已经撤掉。

中间那块为什么碎不了

中央纵墙在项目里始终留在原地。我们把 UE 中的几何和农舍原资产逐项核对，检查中间这块在原资产中如何定义。

  • 23 个部件中，只有编号 0 的部件标记为固定；它没有关联的破坏对象。
  • 部件与破坏点的对应表里，部件 0 对应的区间为空。
  • 网格顶点自带 part 编号，part 0 有 4,078 个三角。UE 端 21,060 个三角逐个能在原资产里找到同一 part 的对应三角，误差在 1e-5 m 以内。

中央纵墙的大部分归部件 0。二层楼板外圈、山墙和墙端分属其他部件，在这个项目里可以分裂。样本地图中的摆放保留了部件 0 的固定属性。原游戏运行时是否还会通过其他途径显示局部破损，目前缺少实机观测。

三个原资产相关的开关

  • -bfvdv：显示墙面局部损伤。在 UE 材质里，用 103 个球体近似距离场，把场内墙面的外观切换到损伤图集。改正坐标方向以后，103 个点都落在各自的部件上。
  • -bfvbreakpart0：项目为固定部件补做的分裂效果。将它的 46 个碰撞凸体分成 28 片，地基和墙脚继续作静态锚点。
  • -bfvmapplacement：采用样本地图中的摆放角度。事件顺序一致，最终碎块高度相差 0.3–0.6 m，drive 测试里有一次删除提前了 16 ms。旋转坐标后的浮点舍入会影响求解。

编辑器里看开销

在编辑器里 PIE，控制台输入 bfv.PerfHud 1，左上角会列出本帧、1 秒均值、5 秒峰值，只算这个工程的破坏开销。数据和 CSV 用同一组打点（BFV_STAT），面板上的数字和报告能直接对照。

还没做

  • 20 栋场景下游戏线程剩下最大的是 15 ms 的骨骼提交和 6.6 ms 的碎屑重建。下一步可以先试：已休眠的簇不再提交骨骼；碎屑改成共享的 InstancedStaticMesh。
  • DV 材质每个墙面像素要算 104 次球距离。可以先试改成累加 dot(v,v)/r²，再按 8 个槽一组提前退出。
  • 原版运行时会不会通过别的路径让 part 0 局部破损，实机数据还是 0 条。

分裂帧与 20 栋压力场景的耗时分解（2026-11-23）

本机 Ryzen 7 7700 / RTX 5060 Ti / Win64 Development / D3D12 SM5 / 1600×900 / Epic / 100% 渲染比例 / 关闭垂直同步与动态分辨率 / 固定 60 Hz / 原生 Havok 2013.2.0-r1（默认纯 2013.2 构建）。 数字从 UE CSV Profiler 的逐帧记录汇总，下面列出测试窗口、汇总口径和两次运行的数值。

1. 测试条件

  • 场景：all 在单栋农舍里每隔 0.4 s 触发一次拆墙，stress 让 20 栋同步执行同一脚本。
  • 窗口：从首次 ReleasePart 所在帧起连续 600 帧（10 s）。"分裂帧"指该帧 Split 耗时 > 0，单栋与 20 栋都是 12 帧。
  • 均值取 600 帧；分裂项的均值 / P95 / 最大只取分裂帧（12 帧时 P95 即最大）。
  • 显示/隐藏对照：同镜头、同破坏时间线；-bfvprobehide 只关碎块组件的可见性，物理照常。RenderThreadTime 与 GPUTime（及 33 个 GPU/* 分项）各自计时，增量按帧对齐相减。
  • 物理步进实际所在线程：默认是游戏线程，每栋农舍在自己的 Tick（TG_PrePhysics）里调 hkpWorld::stepDeltaTime。表中是 20 栋同帧累计。开 -bfvparallelstep 后改在原生 Havok 工作线程池上执行，游戏线程只等它。
  • 分阶段计时用 -bfvphaseprobe：把 stepDeltaTime 拆成等价的 integrate / collide / advanceTime 三段分别计时（已对照 hkpWorld / hkpSimulation 源码确认：本配置是离散仿真 + SAP + 无内存看门狗，两者逐步等价）；addEntity 内部加 tick 时间戳。默认构建不受影响。
  • 每项至少有两次独立运行。下表的峰值取两次中较大者，均值取两次均值的平均。

4. 改动

三项都是开关，默认关闭。默认构建的五种测试模式（release、drive、shoot、all、stress）都和 2026-11-21 的基线逐事件、逐碎块高度一致。

开关 做法 结果是否与默认一致
-bfvdefervisuals 首次脱落时只建刚体、关完好网格碰撞；整簇的渲染组件（创建 + 注册 + 渲染状态）放进队列，按所有农舍共享的每帧预算（默认 1 ms，-bfvvisualbudget=，每栋每帧至少 1 个）在之后几帧建好。建好那一帧才隐藏完好网格，不会露出空洞；分裂前强制建好。 五项全部 identical
-bfvparallelstep[=N] 新的 ABFVStepCoordinator 在所有农舍 Tick 之后、仍在 TG_PrePhysics 内，把 20 个独立 Havok 世界交给原生工作线程池并行步进（每个线程有自己的 hkMemoryRouter；并行期间关闭进程级引用锁，前提是世界间不共享 hkReferencedObject），然后按原顺序完成各农舍后半步。默认线程数 = 逻辑核数 − 2，上限 48。 五项全部 identical
（诊断）-bfvphaseprobe 只加计时 默认构建同样 identical

为什么只推迟视觉、不推迟碰撞：碰撞代理是 Havok 宽相在 addEntity 里同步建的（2060 个代理 3.9–5.5 ms），推迟或改批量 addEntityBatch 都会改变岛与接触顺序，结果不再逐位一致。渲染组件不参与物理，推迟一两帧不影响事件与位置。

6. 走过的弯路（已回退）

  • 碎屑 / 粒子改用 UpdateMeshSection + 预留容量：游戏线程只省 1 ms，CPU 渲染线程却从 9.4 涨到 34 ms（UE 5.8 的 UpdateMeshSection 每帧在渲染线程重写整段顶点缓冲）。这项改动已回退。
  • 一处计时假象：hkStopwatch 首次调用会 Sleep 校准时钟，让第一次分裂看起来要 4 ms。现在 bfvCreateWorld 里提前校准，表中数字已不含它。

7. 下一步

  • 20 栋剩下的游戏线程大头是 EndOfFrameUpdates（15 ms）和碎屑网格重建（6.6 ms，偶发 160+ ms）。前者可以让远处、已休眠簇停止提交骨骼（bNeedPose 机制已在），或合并同栋的阴影网格；后者应换成共享 InstancedStaticMesh / Niagara，或只给玩家农舍开碎屑。
  • 分裂里一半是宽相建碰撞代理；若可以接受与 2013.2 基线不逐位一致，addEntityBatch 能把同帧同簇的子块一次加进世界。

GPU 凸包刚体后端（BFVGpuSim）

2026-11-24 · BFVDestructionUE5

下面按开发的先后记录问题与修复。后面附有同一版 GPU 与 Havok 后端的结构、参数和对照结果。

要做的事

把 RigidSim 搬进这个工程，改成能吃凸包，用农舍的碎块模型；底层是 GPU 上的 GSK（GJK + 单纯形缓存 + TIM），再加上 RigidSim 已有的优化。Havok 不动，作为对照；新后端用 -bfvgpusim 打开。

先在 CPU 上把算法做对

GPU 上调物理很难看到中间状态，所以先写了一份和着色器同一份代码的 CPU 镜像（BfvConvexCore.ush 同时被 C++ 和 HLSL 编译），在 CPU 上把 158 块原叶片从半米高扔到地上，要求全部睡着、不穿地、不互相陷进去。

第一版不睡。追了几轮，问题都在“静止”上，不在“碰撞”上：

  • 作者摆放的叶片本来就互相重叠，最深 0.28 m。穿透恢复放在速度里做，推开的速度就变成了动能，堆子一直抖。改成分离冲量：推开只改位置，不进速度。
  • 只看速度阈值的休眠，打不过接触抖动。照着 Havok 的源码加了两层：低速体每步减速（LOW 类 solver deactivation），以及位置参考盒（物体在 2 cm 的盒子里待够时间才算静止，每 8 帧再用一个 8 cm 的盒子看一次）。
  • 有几对叶片会越陷越深。原因是深穿透时 SAT 选了边轴，流形只剩一个点，物体绕着这个点转进邻居里。现在 SAT 偏向面轴，流形太浅或为空时用一个按 SAT 深度的点兜底。
  • 睡着的体被醒着的体压着时，只吃冲量不积分，等于一堵墙。求解前先把接触到的睡体叫醒，和 Havok 合并岛的行为一样。

做完以后 23 个簇单独落地、158 块、186 块（含地基碎块）全部通过。

搬到 GPU

每步大约 20 个 compute pass：积分和空间哈希、配对、窄相、地面、着色和求解、休眠、回读。几个跟 CPU 不一样的地方：

  • 农舍的大部件直径到 15 m，放不进 RigidSim 的 13 邻格，单独放一个“大体列表”，所有体都和它测。
  • 着色 + 求解原来是每色一次 dispatch，一步 290 个 pass。改成每栋农舍一个 1024 线程的线程组，色与色之间用组内屏障。
  • 结果异步回读，晚 1–3 帧。分裂、删叶的判定在游戏线程用回读的接触事件，规则和 Havok 路径一样。

对齐

5 个回归模式里，部件释放、整簇分裂、支撑门的类型和数量全部一致，结束时全部睡着，没有爆炸。单栋全部打碎（all）落点中位数差 +3.4 cm。

两个没对齐的地方：

  • 20 栋（stress）的落点中位数差在几次运行之间是 +2 到 +12.6 cm。GPU 的原子操作顺序每次不同，结果不能逐位复现。
  • 车撞碎片删叶（速度 > 5 m/s 才删）每次 0–3 个，Havok 固定 2 个。这个规则对车和碎片接触那一帧的速度很敏感。

性能

单位 ms，数字是均值 / P95：

Havok（游戏线程） GPU 步进（GPU） GPU 提交（游戏线程）
单栋 all 0.34 / 0.67 1.29 / 2.70 0.007
20 栋 stress 6.28 / 12.72 3.95 / 5.12 0.017

单栋 GPU 比 Havok 慢，GPU 有大约 0.5 ms 的固定开销（宽相清表、几十个 pass 的依赖链）。20 栋时 GPU 更快，而且物理整个离开了游戏线程：游戏线程上的物理帧从 8.7 ms 降到 6.3 ms，剩下的是分裂和位姿同步，两边一样。

GPU 时间里窄相占大头：每个穿透的凸包对都要做 SAT，20 栋时 22 000 对。已经做了 SAT 轴缓存（浅接触沿用上一步的轴），车只测面轴，窄相大约快了一倍。下一步是把 SAT 的边×边放到一个 wave 里并行。

Havok 不受影响

最终构建不加 -bfvgpusim 跑 5 个模式，事件日志、刚体位置、清醒统计和存档的基线逐位相同。

BFVGpuSim 状态与结果（2026-11-24）

-bfvgpusim = 第二物理后端：GPU 上的凸包刚体（GSK 风格 GJK + SAT + 一次性流形 + 着色 Gauss–Seidel + 暖启动 + 分离冲量 + Havok 式休眠）。Havok 2013 仍是默认路径，开关关闭时没有任何代码路径变化（见文末回归）。

怎么跑

实验在同一 UE 构建中切换后端：默认使用 CPU 上的 Havok，对照组启用项目的 -bfvgpusim 选项。每次都记录事件、数量、休眠和碎块落点。

  • 需要 D3D12 SM6（Config/DefaultEngine.ini 已切 DX12 + PCD3D_SM6）。-nullrhi 下 GPU 后端不能跑（会 Fatal 提示）。
  • 首次启动会编译全部 SM6 着色器（约 1 分钟，之后进 DDC）。
  • 两条路径使用同一批形状。烘焙数据有 481 个凸包，分别来自部件 222 个、叶片 207 个、地基残留 15 个和车身 37 个。
  • 可选参数：-bfvgpuiters=N（求解迭代，默认 4）、-bfvgpumaxbodies=N（默认 8192）、cvar bfv.gpu.MaxColors（默认 24，剩余接触进串行色）。

关键修复（为什么第一版不睡 / 会穿）

  1. Baumgarte 偏置放在速度求解里 → 作者摆放的叶片本来就互相重叠 0.28 m，推出速度变成动能，堆子一直抖。改成分离冲量。
  2. 只看速度阈值的休眠打不过接触抖动 → 加 Havok 的位置参考盒（hkRigidMotionUtilCanDeactivateFinal）和 LOW 类求解器减速。
  3. 深穿透时流形为空/只有 1 点 → 物体倾斜后陷进邻居 0.15–0.25 m。SAT 偏好面轴（边轴要好 5% + 5 mm 才用），流形为空/太浅时用支撑点兜底一个深度 = SAT 深度的点。
  4. 睡着的体被醒着的体压着时只吃冲量不积分 → 求解前“接触即并岛”唤醒。
  5. 农舍大部件（直径到 15 m）在 1.5 m 格子的 13 邻格外 → 大体列表，所有体都和它们测。

阶段分解（all 碎落最忙的 2 秒，每 120 步平均，ms）：宽相 0.27，窄相 1.1–1.4，着色+求解 0.17–0.21，休眠+回读 0.06。20 栋：宽相 0.38–0.53，窄相 3.4–3.6，求解 0.22–0.28（22 000 凸包对、7 200 接触点）。

要点：

  1. 游戏线程：GPU 后端把物理从游戏线程拿走了。20 栋时 Havok 步进 6.3 ms（P95 12.7）在游戏线程；GPU 后端游戏线程只剩 0.017 ms 提交，物理帧 8.7 → 6.3 ms（剩下的是分裂逻辑、位姿同步，两边一样）。
  2. GPU 时间：单栋 GPU 步进 1.0–1.3 ms，比 Havok 单栋 CPU 时间（0.1–0.33 ms）慢；20 栋 3.95 ms，比 Havok 6.3 ms 快且不在游戏线程。GPU 时间几乎不随农舍数线性增长（1 → 20 栋：1.3 → 4.0 ms），因为大部分是固定开销（宽相 0.2 ms、调度链）和窄相长尾。
  3. 窄相是大头：每个穿透的凸包对都要做 SAT（面×点 + 边×边×点，农舍碎块平均 10 顶点 10 条边方向，车身最大 315 条）。已做：SAT 轴缓存（浅接触沿用上一步的轴，每 8 步全量一次，CPU 镜像 6.3 → 2.6 ms/帧，结果不变）、车只用面轴、流形构建只有一个调用点（寄存器/本地数组减半）。

已知差异 / 没做的

  • 回读晚 1–3 帧：分裂和删叶判定用的是 GPU 结果，事件时间比 Havok 晚约 16–50 ms。五个场景的分裂数一致，drive 的删叶数在不同运行间有波动。
  • 地形是一个平面（农舍底下地形中位高度），地形起伏 < 50 cm；Havok 用的是三角网格。
  • 车只做运动学凸包（37 个凸包），轮子不参与。
  • 射线/扫掠查询：静态部件和地面仍在 Havok 世界里做（开炮、车撞部件判定）；碎块射线在 GPU 模式下用回读位姿 + 凸包平面裁剪（GpuRay）。
  • 车：Havok 用 setPositionAndRotation 瞬移车（刚体速度 0），碎块靠穿透恢复被推开；GPU 侧对运动学伙伴也用速度级 Baumgarte 推出（其他接触用分离冲量），车速度默认不给（-bfvgpucarvel 打开）。删叶数仍和 Havok 不稳定一致。
  • 结果不可逐位复现（原子累加、着色优先级与线程调度有关）。
  • Jacobi 对照开关没有接到 UE（CPU 镜像里也只做了 GS）。

回归（Havok 默认路径不变）

在最终构建（DX12 SM6、GPU 插件及所有 GPU 改动）里关闭 -bfvgpusim，release、drive、shoot、all、stress 五种模式的事件日志、刚体位置、清醒统计都与 Havok 基线逐位一致。

下一步（没做完的）

  1. 窄相：SAT 边×边放到 wave 内并行（一对凸包一个 wave，32 线程分摊边对）。当时估算窄相可能提速 3–5 倍，尚待实测。
  2. 宽相固定 0.2 ms：哈希清空 8192 + 13 邻格链表遍历；可以换成排序（按格子 id radix sort）或只在有醒体时跑。
  3. 确定性：着色优先级已是确定的，剩下原子累加顺序（接触槽位、事件槽位）；按 (体对, 凸包对) 排序接触后求解可以逐位复现。
  4. 车：删叶规则对车-碎片速度敏感，可以把 Havok 的车代理容差（10 cm）和 TIM 做进 GPU 的车对。
