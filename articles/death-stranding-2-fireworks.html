游戏效果解析 · DEATH STRANDING 2: ON THE BEACH

《死亡搁浅 2》的花火，
怎么撑得住这么大的场面？

旋转的喷口把火星甩出去，空中是密密麻麻的亮点，下面还有烟、建筑和水面倒影。当时我一直想知道：这么多东西一起动，性能到底怎么压得住？这次终于能把它拆开看了。

DOTAFS · 2026 年 11 月 7 日 · Graphics Systems · 约 12 分钟
研究记录：2026.10.28–11.02；本文 UE 录像：2026.11.07

先看我们拿到了什么

上一篇随笔里，我说过想把这些游戏效果单独写出来。这次先讲二代的花火。我们已经把捕获范围内的场景模型、材质和摆放关系带进 UE，也找到了旋转塔、骨骼挂点以及多种粒子的资源和计算路径。

原游戏的本地视频目前未找到。当时指定的原游戏参考视频在这里，重点可看约 17–25 秒。平台视频的清晰度由其片源和播放器决定；本文暂用上面的捕获图保留可放大核对的画面。

怎样尽量保留画质：采集先存 PNG，网页视频从 PNG 一次编码，不缩放、不补帧、不额外锐化。浏览器兼容的 H.264 仍是有损压缩；检查单颗火星时，请打开 PNG 原图。

第一步，先把场景和喷口找对

花火看起来是一整面金色瀑布，拆资源时却要从摆放对象一路追到嵌套效果、发射器、材质和着色器。我们解析到的这一范围包含 48 个摆放根，其中 25 个带嵌套效果，合计 187 个系统、702 个发射器、71 种 shader。这些是资源图里的数量，不能当作同一帧的粒子数。

这里先走过一次弯路。最早选中的大塔有 43 根骨骼，后来把网格、骨骼和捕获画面对上，才确认目标场景的三座塔对应 35、12、35 根骨骼。喷口跟着骨骼挂点运动，出生位置和喷射方向也跟着变化。家族选错了，粒子参数再接近，整个旋转形状还是会偏。

地图摆放→塔与骨骼挂点→粒子出生与更新→顶点展开→透明度、光照与合成

场景也足够大。后来的 UE 测试中加载了 41,939 个实例，组织为 2,449 个 HISM 组件，也就是 UE 用来管理层级实例的一类组件。它们描述的是我们的场景组织方式；原游戏的完整地图、流送和 LOD 系统没有随之完整移植。

第二步，看 GPU 每一步在算什么

已确认的一部分火星使用计算着色器更新。位置、速度、剩余寿命和类型参数放在 GPU 缓冲区里，着色器按记录处理粒子。这样的数据组织适合并行执行，省去了把每颗火星当作独立场景对象逐个驱动的需要。

在捕获的一个更新分支里，我们恢复出了重力、阻力和位置积分。先修改速度，再用新速度推进位置，可以写成下面的形式。

v′ = (v + Δvgravity) × (1 − drag(age))
p′ = p + v′ × Δt

p 是位置，v 是速度，age 是归一化年龄。这里的 Δvgravity 是该次 dispatch 输入的速度增量，不能再盲目乘一次 Δt。捕获时间步约为 0.017404 秒；这不证明原引擎始终使用固定时间步。

这次核对很直接：拿更新前后的原始缓冲区比较。类型 13 的 188 条匹配记录中，186 条速度结果达到 float32 位级一致；类型 16 是 2,643 条中的 2,630 条。类型 12 还有 curl 扰动，单靠上面的核心就对不齐，不能把它算成已经完整恢复。

对应到 UE，我们把正确大塔家族的 256 个源 GPU 喷口组织进 4 个 GPU 发射器池，按来源参数计算出生位置和形状，减少独立发射器的管理工作。这是复刻采用的组织方式，目前没有证据说原游戏也恰好用了这四个池，更没有单独测出这项合并省了多少毫秒。

第三步，一颗火星只需要多少几何？

一条飞出去的亮线，可以由少量顶点展开。我们核对的地面火星分支采用八个顶点、六个三角形，形成三段结构。它根据视线和速度在屏幕平面的投影决定拉伸方向，再结合宽高比和枢轴位置生成轮廓。重建时曾用四顶点贴片近似，后来才把这段展开规则补回来。

在三次选定绘制中，共 181 个粒子、1,448 个执行顶点，CPU 重建的最大位置误差约为 35 微米。再把捕获输入送进 UE，只画不透明白色轮廓，在原视点、6° 放大投影下，参考与重建只差一个边界像素，轮廓 IoU 为 99.94%。这回答的是这条 position 分支有没有对上，不包含颜色、光照、运动矢量和随机模拟。

展开固定输入的轮廓验证图

远处火星还有屏幕宽度处理。检查过的部分类型把距离、寿命和随机量带入宽度公式，其中一条分支保留约 1.5 像素的最小贴片宽度，帮助细小火星维持可见。它主要控制视觉稳定性，不能直接算作降低 GPU 开销；透明粒子的成本还与覆盖多少像素、重叠多少层有关。

第四步，为什么搬过去以后亮成一片？

比较意外的是，静态导出的某些透明度贴图是全白的，运行时真正绑定的对应层却带着柔和的 Alpha。只盯着资源文件，很容易漏掉这个差别。

图 4。两张图均为 32×32 源数据的 Alpha 通道可视化，按整数倍放大，没有平滑或生成细节。运行时层来自事件 86435 的资源 3464。

对类型 12、16、18，按报告中相同圆遮罩和采样方式积分，旧方案得到 0.34144，现场贴图得到 0.09374，相差约 3.64 倍。类型 13、17 的这项比值则为 1。这个发现解释了特定粒子为什么显得太实、太满；3.64 倍描述的是该项遮罩积分，不能直接当作整幅画面的亮度倍率。

寿命也会改变效果。已经核对的部分火星会随剩余寿命缩短，颜色按当前年龄更新；如果只在出生时取一次颜色，或者让长度一直保持最大值，粒子尾部就会残留得过久。这些细节叠起来，才决定画面是细碎的火星，还是一片厚重的发光物。

原游戏的 GPU 状态，我们实际测到了什么？

抓帧帮助我们找到数据和 shader，实时测量则回答它们用了多少 GPU 时间。下面是原游戏进程中已识别管线的时间戳记录。采样时连接了 RenderDoc，没有运行视频编码器；这些标签沿用采集器的 generic 与 chiral 分类，不代表已经覆盖全部花火。

这组数值来自另一次向上的参考镜头。它包含已识别的烟、火和粒子管线，遗漏的管线与共享光照不在统计内；各类工作时间相加也不必然等于整帧关键路径。因此，不能写成“整场花火只要 0.86 ms”。

一条实测样本中的 GPU 提交状态

最后一个有效样本记录了 generic / chiral 绘制调用 109 / 7 次，模拟调用 2 / 5 次，间接调用 8 次，涉及队列 1 个，丢弃查询 0。它是单个样本的状态，不是整段采样的平均调用数。

间接绘制把绘制参数放进缓冲区，再由 GPU 执行。参数缓冲区既可由 CPU 生成，也可由 GPU 生成；仅看到 ExecuteIndirect，不能自动证明某套 GPU 剔除算法已经生效。尤其不能把命令数量或缓冲区容量当作活跃粒子数。参见 Direct3D 12 的定义。

UE 的粒子测量用了另一种方法：在场景运行中按关、开、关、开的顺序切换选定系统，比较整帧 GPU 活跃时间。正确塔家族那轮实验的平均增量为 1.42792 ms，两次配对分别为 1.47374 和 1.38210 ms。它包括粒子开关连带的反射和共享光照变化。镜头、分辨率、数量及计时范围与上表不同，不能相除得出移植后的性能比例。

大场景的开销，还藏在花火后面

把地图搭进 UE 以后，我们发现大量被遮住的实例仍然进入了深度和基础材质绘制。开启 GPU 实例 HZB 遮挡剔除后，GPU 先利用分层深度图判断实例是否被前方物体挡住，再减少后续提交的几何。这项修改发生在 UE 复刻场景中。

同条件 ABAB · 2026.11.02关闭剔除开启剔除
整帧 GPU 时间 ↓12.9701 ms8.1331 ms
主视图 PrePass + BasePass ↓5.625 ms1.320 ms
整帧耗时 ↓15.3227 ms15.3726 ms
实际吞吐 ↑65.26 FPS65.05 FPS

UE 5.8.1 / D3D12 SM5 / RTX 5080。主视图 1284×722，反射 768×432；同轮保留相同几何、材质、阴影、反射及 10 个活跃效果。数值不是本文 1080p 录像的性能。

GPU 明显轻松了，帧率却没有涨。原因要继续往 CPU 和渲染任务看：主线程、编辑器界面，以及阴影和网格准备会影响整帧推进。拿 8.13 ms 的倒数宣称 123 FPS，会漏掉这些等待。

随后另一轮实验把主视图和阴影的网格收集任务从 4 份拆成 16 份，实际吞吐从 67.05 提升到 70.28 FPS，约 4.82%。这轮的播放方式和活跃效果数量与前一轮不同，单独记录。它说明了我们怎样找复刻场景的瓶颈，还不能反过来证明原游戏用了完全相同的调度。

现在可以解释的，是一部分具体做法：批量更新粒子，让少量几何承担火星的轮廓，再由挂点、寿命、透明度组织出密集的运动。至于一个大场景能否流畅，仍要把几何、烟雾、反射和 CPU 提交一起测。单看粒子数量，很难猜准最后的成本。

这次知道了什么，还差什么

这次最开心的地方，是原本只能隔着屏幕猜的东西，已经能对应到一份输入、一次计算和一个结果。我们找到了这段场景，找对了旋转塔，也能把某一类火星的顶点位置对到很小的误差。接下来要继续补的是原始随机流、风与力场、碰撞、上一帧位置和运动矢量，以及烟雾、光照和后处理。本文的 UE 画面仍是研究重建。
