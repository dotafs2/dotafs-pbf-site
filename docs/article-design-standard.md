# DOTAFS 论文学习笔记设计规范

版本：1.0  
生效日期：2026-08-14  
适用范围：DOTAFS 网站内所有论文笔记、技术学习文章及其交互解释页面。

本文件是项目的长期验收标准。以后新增文章或大幅重构旧文章时，必须先完整阅读本文件。若某篇文章确实不适合其中一项，应在实现说明中明确指出原因，不能静默忽略。

## 1. 页面定位

DOTAFS 的文章是“可以验证和操作的研究笔记”，不是新闻摘要、论文翻译、营销落地页或演示文稿。

每篇文章只有一个核心任务：让读者知道论文试图解决什么、方法为什么这样设计、证据是否支持结论，以及它与实际图形学或物理模拟工作如何连接。

文章的主要视觉记忆点应来自以下内容之一：

- 原论文的关键架构图；
- 能解释因果关系的交互实验；
- 一张清楚的实验对比表；
- 与项目技术栈对应的模拟例子。

不得把巨型标题、口号、渐变背景或装饰动画当作页面记忆点。

## 2. 强制内容架构

长篇论文笔记默认按照以下顺序组织。标题可以根据论文内容改写，但不能丢失对应问题。

### 0. 论文信息

首屏紧凑展示：

- 论文完整标题；
- 作者、机构、会议或预印本状态、版本日期；
- 论文、项目页和代码链接；
- 一至两句话说明论文实际完成了什么；
- 输入、输出、任务范围与主要技术组件；
- 合理的阅读时间。

首屏不得使用 `100vh` 强行占满窗口，也不得加入与论文内容无关的宣传文案。

### 1. 他们想解决什么问题

这一节承担论文 Abstract 和 Introduction 的作用，必须回答：

1. 现有方法卡在哪里；
2. 为什么这个问题值得解决；
3. 论文的输入和输出分别是什么；
4. 作者真正提出了什么，而不只是展示了什么；
5. 方法明确不解决哪些问题。

先用一段准确的自然语言概括，再使用问题、原因、贡献、边界四格或等价的紧凑结构。不能只复制摘要，也不能用空泛的“革命性”“突破性”替代具体任务。

### 2. 相关工作与路线比较

至少比较三条真正不同的技术路线，或者论文中最重要的三个基线。比较表应尽量包含：

| 比较项 | 应回答的问题 |
|---|---|
| 世界或状态表示 | 像素、latent、点云、mesh、particle、Gaussian，还是显式物理状态？ |
| 动力学来源 | 解析求解器、数据学习、生成模型，还是混合方法？ |
| 条件与输入 | 文本、视频、动作、几何、材料参数分别进入哪里？ |
| 输出可用性 | 只能观看，还是能查询、编辑、碰撞、继续模拟？ |
| 优点 | 它在哪个评价标准上更强？ |
| 代价与限制 | 数据、算力、稳定性、泛化或可解释性问题是什么？ |

比较必须说明“这篇论文改变了哪一步”，不能只罗列论文名称。

### 3. 先给完整方法地图

进入细节前，用一张架构图和一段短总结建立全局认识：

```text
输入 → 状态表示 → 核心预测/求解 → 校正或解码 → 输出 → 评估
```

优先使用论文自己的总览图。旁边只标出读图顺序、每个模块的输入输出和本文最关键的创新点，不把整段正文塞进图里。

### 4. 方法细节：由浅入深

每个核心模块使用同一套解释顺序：

1. 这个模块为什么存在；
2. 它接收什么数据；
3. 内部具体做什么；
4. 输出传给谁；
5. 去掉它会出现什么问题；
6. 用图形学、PBD、粒子、约束、碰撞或编辑器中的具体例子解释。

公式必须同时解释变量的物理或几何意义。不要只展示公式截图。若概念包含状态变化、空间关系或参数影响，优先做一个小型交互实验，让控件变化能直接改变图和解释文字。

### 5. 实验与证据

实验部分必须区分以下信息：

- 数据集与场景；
- 训练或推理资源；
- 对比基线；
- 指标方向，明确越高越好或越低越好；
- 定量结果；
- 定性结果；
- 消融实验；
- 失败案例；
- 论文没有报告的内容。

不得只摘出最好看的案例。若论文没有定量指标、没有消融、没有运行时间或没有用户研究，应明确写出“论文未报告”，不能替作者补结论。

### 6. 它比别人好在哪里

优势必须和具体比较对象绑定，例如：

- 相比纯视频生成，它是否提供显式几何或可编辑状态；
- 相比纯解析模拟，它是否能识别材料或补偿系统误差；
- 相比逐对象优化，它是否能够跨对象泛化；
- 相比端到端网络，它是否保留物理约束和可解释性；
- 相比其他模型，它在哪个指标、数据规模或执行速度上占优。

避免“效果更好”“能力更强”这类没有比较对象和证据的句子。

### 7. 局限、失败与适用边界

至少回答：

- 在哪些材料、动作、相机或场景上可能失败；
- 长时间 rollout 是否会积累误差；
- 是否满足守恒、接触和拓扑一致性；
- 是否依赖封闭模型、大规模数据或昂贵硬件；
- 输出是视觉上合理，还是可以作为可靠物理状态；
- 当前版本是经过同行评审的论文还是预印本。

局限必须与优势同等具体，不放在一句免责声明里带过。

### 8. 对项目的实际映射

结尾给出一条可以执行的技术路线，而不是再次重复摘要。例如：

```text
PBD 状态与真实轨迹
→ 材料参数估计
→ 原有 PBD 约束求解
→ 小型网络预测位置或速度残差
→ 与纯 PBD、纯网络进行误差和稳定性比较
```

明确哪些部分现在可以做成小实验，哪些需要数据，哪些只值得继续观察。

### 9. 参考资料与素材声明

文章底部列出论文、项目页、代码和数据集。所有第三方图片必须能追溯到来源，并同步维护 `THIRD_PARTY_NOTICES.md`。

## 3. 使用原论文文字、图片和数据

### 原文引用

- 只有在作者的原始措辞本身很重要时才直接引用。
- 单个来源的逐字引用保持短小，通常不超过 25 个英文单词。
- 引文旁边给出中文解释和准确链接，不能让引文代替分析。
- 其余内容使用自己的语言概括，并区分“论文声称”和“本文推断”。

### 论文图片与截图

一篇长文通常应选择 2–4 张真正关键的原论文图；数量服从解释需要，不为凑数。

每张图都必须包含：

- 原 Figure 编号或页面位置；
- 一句“读图时看什么”；
- 来源链接；
- 是否裁切、标注或重绘；
- 必要的版权或许可说明。

优先下载到项目内稳定保存，不依赖容易失效的外链。不得拉伸图片，不得用低清截图替代可获得的原始图。许可不明确时，只使用解释所必需的有限图像摘录并清楚署名；如果无法合理使用，则自行重绘结构图并注明依据。

### 表格与数据

- 重要实验表优先转录成可访问的 HTML 表格，而不是只贴截图。
- 保留原始数值和指标方向，不擅自标准化或换算。
- 最佳结果的视觉强调应克制，并写清是否来自作者报告。
- 手机端表格允许横向滚动，不能压缩到无法阅读。

## 4. 示例与交互原则

交互只用于解释一个真实关系：参数如何影响状态、动作如何改变未来、模块如何改变输出，或者一种方法为什么优于另一种方法。

每个交互必须具有：

- 明确的问题或观察目标；
- 可识别的输入控件；
- 立即可见的状态变化；
- 随状态更新的文字解释；
- 重置方式；
- 键盘焦点与移动端可操作性；
- `prefers-reduced-motion` 支持。

禁止只有粒子漂浮、网格闪烁或自动轮播，却不能帮助理解论文的方法。动画不应让正文或按钮长时间处于不可点击、不稳定或不可见状态。

## 5. 视觉系统

### 整体气质

使用克制的石墨研究手册风格，接近长期阅读的技术博客，而不是 AI 产品宣传页。页面依靠排版、边线、留白和内容密度形成层级。

### 色彩

基础语义色限制为三类，允许使用透明度产生层次：

| 角色 | 建议值 | 用途 |
|---|---|---|
| Graphite | `#1b1d1f` | 页面背景与最深面板 |
| Warm white | `#ece9e2` | 标题、正文和主要状态 |
| Stone gray | `#969792` | 次要文字、标签和低饱和提示 |

模块区分优先使用 `rgba(255,255,255,.03)` 的表面差、`rgba(255,255,255,.12)` 的细边线和空间关系。确有语义需要时可以增加一种低饱和强调色，但必须全篇只承担同一个含义。

禁止荧光绿、鲜艳紫色、大面积蓝色渐变、彩色发光和玻璃拟态。

### 字体

全站文章只使用两套字体：

- `Noto Sans SC`：标题、正文、按钮；
- `IBM Plex Mono`：数据、代码、图注标签、论文元信息。

不得为单篇文章额外引入展示字体。粗体只用于结论、变量和真正需要扫描的标签。

### 字号与阅读宽度

| 元素 | 桌面端 | 移动端 |
|---|---:|---:|
| H1 | 30–38 px | 26–30 px |
| H2 | 22–26 px | 20–23 px |
| H3 | 16–18 px | 16–17 px |
| 正文 | 15–16 px | 15 px |
| 图注/元数据 | 10–12 px | 10–12 px |

正文行高保持在 `1.7–1.85`。主阅读列约 `680–760px`，目录约 `210–240px`，整页内容宽度通常不超过 `1120px`。

### 空间与模块

- 一个普通章节的上下间距通常为 36–56px，不制造连续的大面积空白。
- 使用 1px 边线、轻微表面明度差和标题层级区分模块。
- 卡片只用于真正可独立比较或操作的内容，不给每个段落套卡片。
- 圆角保持 0–3px，不使用漂浮的胶囊标签作为装饰。
- 编号只用于真实顺序、实验步骤或目录，不作装饰。

### 首屏和标题

- H1 不得成为覆盖整个屏幕的海报。
- 不使用“重新定义未来”“让想象成为现实”一类宣传口号。
- 首屏应尽快出现论文任务、输入输出或方法图。
- 不把摘要拆成多张数据卡来制造产品感。

## 6. 写作语气

- 使用清楚、具体、可验证的中文。
- 先说结论，再解释术语。
- 技术名词首次出现时给出一句定义，此后保持同一译法。
- 例子自然使用粒子、约束、布料、碰撞、材质、Three.js、Blender 或编辑器工作流，不写“专门面向某职业”的标签。
- 不重复同一段总结，不用无意义的过渡文填充篇幅。
- 篇幅由证据和解释决定；长文应增加图、表、实验和推导，而不是放大字体或增加空白。

## 7. 首页文章卡同步

新增或大幅修改文章时，同时检查：

- `home/index.html`；
- `home/en/index.html`；
- 标题、发布日期、分类、阅读时间和摘要；
- 中英文入口是否指向同一篇文章；
- 首页文章数量是否正确。

英文首页卡只需要忠实描述文章，不要求整篇中文笔记自动复制成英文版，除非用户明确要求。

## 8. 完成前的验收清单

### 内容

- [ ] 研究问题、输入输出和任务边界明确。
- [ ] 有相关工作或基线比较。
- [ ] 有一张完整方法地图，再进入模块细节。
- [ ] 关键模块按输入、处理、输出、必要性解释。
- [ ] 实验设置、指标、结果和证据强度明确。
- [ ] 优势绑定具体基线或指标。
- [ ] 局限和失败案例没有被隐藏。
- [ ] 论文事实与本文推断可以区分。
- [ ] 原论文、项目页、代码和图片来源完整。

### 视觉与交互

- [ ] 没有巨型标题、口号、渐变、荧光或无意义动画。
- [ ] 全文最多两套字体和一套低饱和色彩系统。
- [ ] 图片清晰、比例正确、图注完整。
- [ ] 表格在手机端仍可阅读。
- [ ] 所有控件会改变可见状态和解释文字。
- [ ] 键盘焦点、减少动态效果和语义标签可用。
- [ ] 桌面 1440px 与移动 390px 均无横向溢出。
- [ ] 图片 `naturalWidth > 0`，Canvas/3D 视图尺寸合理。
- [ ] 浏览器没有页面错误或控制台错误。

### 工程与发布

- [ ] 保留已有编辑器、PBF 页面、导航和文章交互。
- [ ] 第三方素材已写入 `THIRD_PARTY_NOTICES.md`。
- [ ] 相关测试和生产构建通过。
- [ ] 没有提交 `node_modules`、`dist`、日志、浏览器配置或临时文件。
- [ ] 只有在用户当次明确要求时才提交和推送。

## 9. 推荐文章骨架

```text
论文信息
├─ 一句话任务
├─ 输入 / 输出 / 边界
└─ 原论文与代码

1. 研究问题
├─ 原方法为什么不够
├─ Abstract 的准确概括
└─ 本文贡献与不做的事情

2. 相关工作
└─ 路线、表示、优点、代价比较表

3. 方法总览
├─ 原论文架构图
└─ 完整数据流

4. 方法细节
├─ 模块 A：输入 → 处理 → 输出
├─ 模块 B：输入 → 处理 → 输出
└─ 一个可操作例子

5. 实验
├─ 设置与指标
├─ 主要结果表
├─ 消融
└─ 失败案例

6. 优势与比较
7. 局限与适用范围
8. 对当前项目的实现映射
9. 参考资料与素材声明
```

这套骨架是为了保证研究逻辑完整，不要求所有文章长得完全相同。文章可以根据论文对象选择不同的关键图和交互，但不能退化成巨型标题、短文案和装饰卡片组成的模板页。
